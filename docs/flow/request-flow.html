From a station owner's request to an approved, bookable station

Step by step

  1. 1

    Owner signs up

    The owner creates an account in the Business App with email and password. Supabase Auth confirms the email with a link or 6-digit code, then gives the phone a signed login token. The app sends this token with every later request, and refreshes it automatically.

    Saved in: Supabase Auth user list (password stored only as a secure hash) and profiles (name, phone).

  2. 2

    Creates the business and a station

    The app asks the database to create the business. The database reads the user id from the token and makes that person the owner. The app cannot pick its own role. A new station always starts as a draft with an empty application.

    Saved in: businesses, business_members, stations, charging_points, station_operating_hours, station_applications.

  3. 3

    Uploads documents

    Files go to a private storage folder for that business, with a random file name. Only members of that business and platform reviewers can open it. A row in the database points at the file.

    Saved in: Storage station-documents/{business}/{station}/… and the table station_documents.

  4. 4

    Submits for review

    The database checks that the station has at least one charging point, opening hours and every required document. If anything is missing, it refuses with a plain message. If all is there, the status becomes Submitted and every reviewer gets a notification.

    Saved in: station_applications (status), application_events (timeline), notifications.

  5. 5

    Admin Panel shows it live

    Realtime pushes the new notification to any open Admin Panel, and the application appears in the review queue. Only platform staff with the review permission can see the queue.

    Read from: notifications, station_applications. Nothing new is saved.

  6. 6

    Reviewer checks documents

    A reviewer signs in to the Admin Panel the same way, through Auth. Each document opens through a link that expires after 5 minutes. The reviewer approves it or asks for a correction with a note. Nobody can review a business they belong to.

    Saved in: document_reviews (permanent history) and the status on station_documents.

  7. 7

    Admin approves

    An admin with the decide permission approves the application, or rejects it with a reason. On approval the station becomes Active and the business becomes verified. The audit log records who did it and when.

    Saved in: station_applications, stations, businesses, audit_logs, notifications.

  8. 8

    Owner gets a push

    Every minute the scheduler runs the notification sender. It reads the waiting notifications and sends them through Firebase to the phones registered for that business. The notification also appears in the app's list, even when push is off. The station can now take bookings.

    Read from: notifications, device_tokens. Each message is marked as sent.

  1. 1

    Driver reserves a slot

    A signed-in driver picks a charging point and time. The database holds the slot for 10 minutes while they pay. A database rule makes it impossible for two bookings to overlap on the same point, even when two people tap at the same moment.

    Saved in: bookings (status payment pending), booking_events.

  2. 2

    Payment starts

    The app asks an Edge Function to start payment. The function reads the fee from the database (₹12 today), never from the phone. It then creates a Razorpay order using the secret key, which only the server holds.

    Saved in: payment_orders. Fee comes from platform_settings.

  3. 3

    Driver pays ₹12

    The driver pays in Razorpay's own checkout screen, by UPI or card. ChargeKaro never sees card details. The charging fee is not part of this payment: the driver pays the station directly.

    Saved at: Razorpay. ChargeKaro stores only the payment and order IDs.

  4. 4

    Payment is recorded once

    Razorpay notifies the webhook, and the app also asks for verification. Both check Razorpay's signature, and the payment is recorded only once even if both arrive. The booking becomes Confirmed and the ledger adds the fee in paise, minus Razorpay's fee.

    Saved in: payments, ledger_entries, bookings, booking_events, notifications.

  5. 5

    Station sees it live

    Realtime updates the Bookings screen on the staff's phone straight away. Staff also get a push notification through Firebase.

    Read from: booking_events (only for stations that staff member is assigned to).

  6. 6

    Staff check the driver in

    Staff scan the driver's QR code or type the booking code. The database checks four things: the booking belongs to this station, the staff member is assigned there, the fee is paid, and it is inside the check-in window. The car then charges, and the driver pays the station directly.

    Saved in: check_ins, bookings (status), booking_events.

  7. 7

    Background clean-up

    Every minute the scheduler releases unpaid holds and marks no-shows after the grace period. It also sends any due refunds to Razorpay under the refund policy.

    Saved in: bookings, refunds, ledger_entries.

How every request is checked

This is what the green security gate in the map does. Every request takes this path, whether from the Business App, the Admin Panel or the future Retailer App.

  1. 1 · Token attachedThe app sends its login token. Without one, the request is treated as anonymous and can read nothing.
  2. 2 · Token verifiedSupabase checks the token's signature and expiry. A forged or old token is rejected.
  3. 3 · User identifiedThe database learns the user id from the token, and nothing else from the phone is trusted.
  4. 4 · Role looked upThe role comes from the database (business_members, platform_staff), never from the app. A changed app cannot claim admin.
  5. 5 · Rule appliedRow-level security filters what they can read. Actions like approve or check in re-check permission and status.
  6. 6 · Saved & loggedThe change is written, and sensitive actions add a row to the audit log, which nobody can edit.

Keys and connections

Safe to put inside the apps

  • Supabase project URL
  • Supabase publishable (anon) key. It only lets the app talk to the gate, and the gate decides everything.
  • Google Maps key, restricted to the app's package name
  • Firebase app config files

Server only, never in an app or on GitHub

  • Supabase service-role key, used only inside Edge Functions
  • Razorpay key secret and webhook secret
  • Firebase service account (for sending push)
  • Scheduler secret, which protects the background functions

Secrets are added once with supabase secrets set on your Supabase project. The apps refuse to start if someone builds them with a secret key by mistake.
